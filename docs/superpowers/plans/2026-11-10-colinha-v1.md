# Colinha v1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship Colinha, a single-page web app that turns a person's CPF, address and Pix key into Apple Wallet passes. Each pass is built on their iPhone, and nothing personal is sent anywhere.

**Architecture:** One Cloudflare Worker on the free plan serves the Svelte app as static assets and answers one endpoint, `POST /api/sign`. The phone builds the whole pass and sends only the 32-byte SHA-256 of its `manifest.json`. The Worker returns a CMS detached signature made with the Pass Type ID key. The phone then zips the `.pkpass` and hands it to Safari, which opens the Wallet sheet.

**Tech Stack:** Svelte 5 (runes), Vite, TypeScript (strict), pnpm, `@cloudflare/vite-plugin` and Wrangler, WebCrypto, `fflate` (zip), `uqr` (QR as SVG), Vitest with `@cloudflare/vitest-pool-workers` and `@testing-library/svelte`, Playwright (WebKit).

**Spec:** the "Product spec" section below. Task 1 copies it to `docs/superpowers/specs/2026-11-10-colinha-design.md`.

**Execution:** subagent-driven (recommended). The signer, the pass builder and the UI meet at narrow interfaces, and a signing bug would break every pass, so a fresh reviewer per task pays off.

---

## Context

Newcomers to Brazil, and many Brazilians, are asked for their CPF, CEP and Pix key all day: at the pharmacy, on forms, for deliveries, when friends pay them back. Most can't remember them. Colinha turns those numbers into Apple Wallet passes, so they're two taps away, even offline.

Apple only installs signed passes, and the signing key can't safely ship in the browser. So the phone builds each pass, and the only thing that leaves it is an unreadable 32-byte fingerprint, which a Cloudflare Worker signs. To change their data, people come back to the site, or tap "Editar este cartão" on the back of the pass. The site then re-issues the same pass.

## Product spec

### Decided with you
- Apple Wallet only, for now.
- A hash-only signer on the Cloudflare Workers free plan.
- Portuguese and English. The UI follows the phone's language.
- v1 cards: Documentos, Endereço and Pix.
- Name: Colinha.
- Framework: Svelte 5.
- An iOS 26 look: cards stacked like in Wallet, floating glass buttons, sheets that slide up, and as little text as possible.

### My calls (please check these)
1. Plain Vite + Svelte, without SvelteKit. One Worker serves both the assets and the API from the same origin, so the CSP can allow `connect-src 'self'` and nothing else.
2. Passes are written in the UI language at the moment they're created (no `pass.strings`). Re-issuing from a phone set to the other language switches the pass's language. This also avoids two known trouble spots: Apple requires UTF-16 strings files, and Wallet's choice of `.lproj` folder is unpredictable.
3. The UI is monochrome. The passes are the only color.
4. Saved cards live in `localStorage`. Each pass also carries an "Editar este cartão" link with the card data after the `#` in the URL, a part browsers never send to a server. That link restores the card even after Safari clears site data (it does this after 7 days without a visit).
5. No CEP lookup, since it would send the CEP to a third party. iOS AutoFill fills in the address instead.
6. `/` follows the phone's language. Static `/pt/` and `/en/` pages exist for search engines and for shared links.
7. Any language other than Portuguese or English gets English.
8. No analytics. The request count for `/api/sign` in the Cloudflare dashboard serves as the "passes made" number.
9. Six pass colors. The CPF barcode is on by default.
10. Open source, under the MIT license.
11. People can keep several cards of one type, such as two Pix keys or a child's documents. (＋) opens a floating sheet that lists the three card types.
12. iPad can't add passes to Wallet, so it gets the "Continuar no iPhone" handoff, the same as a computer.
13. A Pix name or city that folds to nothing, such as a name in a non-Latin script, is blocked with `error.latin`. Banco Central's code needs at least one character there.
14. If the browser can't open Wallet directly, the fallback is a Safari download: the person taps the downloaded file. Pass bytes never go through the Worker.

### Not in v1
The Saúde card, Google Wallet, pass push updates (`webServiceURL`), CEP lookup, accounts or sync, analytics, per-document landing pages, other languages.

### Cards

All fields are stored normalized: digits only for CPF and CEP, and the payload form for the Pix key. An empty string means "not provided". The pass style is `generic`. Header fields are not used. Every pass back ends with the edit link and the disclaimer.

Number fields on the back of the pass get `dataDetectorTypes: []`, so a CPF isn't read as a phone number. The edit link keeps link detection. Apple's limits for generic passes: 1 primary field, up to 4 secondary and up to 4 auxiliary. With a QR code, secondary and auxiliary share 4 between them.

**Documentos** (default color: Grafite)

| Field | Required | Input | Rule | On the pass |
|---|---|---|---|---|
| CPF | yes | `inputmode=numeric`, mask `000.000.000-00` | mod-11 check digits | primary |
| Nome | yes | `autocomplete=name`, max 40 | not empty | secondary |
| RG | no | max 20, uppercase | none | auxiliary |
| RNM | no | `A–Z0–9-`, max 12, uppercase | none | auxiliary |
| Passaporte | no | `A–Z0–9`, max 12, uppercase | none | auxiliary |
| Código de barras | switch, on by default | — | — | `barcodes`: Code128 of the CPF digits, then a QR of the same digits as a fallback |

**Endereço** (default color: Azul)

| Field | Required | Input | Rule | On the pass |
|---|---|---|---|---|
| CEP | yes | `inputmode=numeric`, mask `00000-000`, `autocomplete=postal-code` | 8 digits | primary |
| Rua e número | yes | `autocomplete=address-line1`, max 60 | not empty | secondary |
| Complemento | no | `autocomplete=address-line2`, max 30 | none | auxiliary |
| Bairro | no | `autocomplete=address-level3`, max 30 | none | auxiliary |
| Cidade | yes | `autocomplete=address-level2`, max 30 | not empty | auxiliary, shown as `Cidade - UF` |
| Estado | yes | native `<select>` of the 27 UFs, `autocomplete=address-level1` | one of the UFs | joined with Cidade |
| Referência | no | max 60 | none | back only |

The back of the pass starts with the full address, written in Brazilian format. Parts that are missing are dropped without leaving stray commas:
```
Rua Augusta, 1500, Apto 42
Consolação, São Paulo - SP
01310-100
```

**Pix** (default color: Turquesa)

| Field | Required | Input | Rule | On the pass |
|---|---|---|---|---|
| Chave Pix | yes | `autocapitalize=off`, `autocorrect=off`, `spellcheck=false` | one detected type; if the input is ambiguous, a segmented "CPF \| Celular" control the user must pick from | primary (formatted) |
| Nome | yes | prefilled from the most recently updated Documentos card | not empty after `toPixText`, otherwise `error.latin` | secondary |
| Cidade | yes | prefilled from the most recently updated Endereço card | not empty after `toPixText`, otherwise `error.latin` | back |

The barcode is a QR code of the BR Code payload. The back shows the "Pix copia e cola" payload (with data detectors off) and the city. The detected key type appears as a small word at the end of the key row (for example "E-mail" or "Celular").

Flows:
- **New card:** (＋) opens a floating sheet that lists the three card types. On an empty Home, the three dimmed cards do the same job.
- **Add:** tap the badge. If anything is invalid, focus the first invalid field and mark it. Otherwise, check the browser (see guards). Then, at the same time, play the "pocket" animation and run `buildPkpass`. Save the card, then call `deliverPass`. When the page is visible again (`visibilitychange`), close the Editor; Home shows the card.
- **Fail:** show a toast with the error copy. The preview returns to its place and nothing is lost.
- **Edit:** tap a card on Home, or open the pass's edit link. The Editor opens prefilled, and the `#` part is removed from the address bar.
- **Delete:** show a confirmation sheet, then remove the card locally. The pass stays in Wallet, and the sheet says so.
- **Erase everything:** from the info sheet, after a confirmation.
- **Guards:**
  - Inside an in-app browser (Instagram, Facebook, TikTok and so on): a banner, and an "Abrir no Safari" capsule in place of the badge that copies the link.
  - On a computer or an iPad (iPad can't add passes): a "Continuar no iPhone" capsule that opens a QR code of `encodeEditLink(card)`. The phone camera opens Safari with the card already filled in.
  - On Android: a short notice.

### Privacy and security model
- The app makes one kind of network call: `POST /api/sign` with a 32-byte body. Everything else is same-origin static files.
- `pass.json` contains the card's random 128-bit serial number. That makes the manifest hash impossible to brute-force back to a CPF, even though there are only about a billion possible CPFs.
- The Worker keeps nothing. It has no storage bindings and logs no request data. Workers Logs are on by default for new Workers, so the config turns them off, and Task 13 checks the dashboard to confirm.
- **Known risk:** `/api/sign` signs any hash it receives, so anyone could sign their own pass under our Pass Type ID. Mitigations:
  - A same-origin check (`Sec-Fetch-Site`) and a per-IP rate limit.
  - If the endpoint is abused, revoke the certificate and issue a new one. Keeping the same Pass Type ID means updates still work.
- The edit link's data ends up in the user's own Safari history. The app removes it from the address bar on load.
- The CSP is strict. There are no third-party resources and no cookies.

## Global Constraints

- The only request the app makes is `POST /api/sign` with exactly 32 bytes. The CSP sets `connect-src 'self'`. There are no third-party scripts, fonts, images, analytics or cookies.
- The Worker has no storage bindings and logs nothing about requests (`observability.enabled: false`).
- Locales are `pt` (pt-BR) and `en`. The UI uses the first entry of `navigator.languages` that matches `pt*` or `en*`, and falls back to `en`. The exception: `/pt/` and `/en/` force their own language through `<meta name="colinha-locale">`.
- These identifiers are fixed before the first public pass and never change:
  - `SITE_ORIGIN = 'https://colinha.app'` (a placeholder until you register the domain).
  - `PASS_TYPE_ID = 'pass.app.colinha.card'`.
  - `ORG_NAME = 'Colinha'`.
  - The serial number: 32 lowercase hex characters from `crypto.getRandomValues`, permanent for each card.
- Visible text comes only from the Copy table. Every action keeps the same name throughout.
- No government marks (coat of arms, gov.br, Receita Federal) and no Pix logo. Every pass back carries `pass.disclaimer`.
- Apple's "Add to Apple Wallet" badge is used unmodified, following Apple's guidelines. "Apple" and "iPhone" stay out of the product name and the domain.
- Svelte 5 runes only, no legacy stores. TypeScript strict. `{@html}` is allowed only in `src/ui/Qr.svelte`, for the SVG that `uqr` produces.
- Runtime dependencies are `svelte`, `fflate` and `uqr`. Anything else needs a stated reason.
- Wrangler 4.36 or later, which the rate-limit binding needs.
- **Targets:**
  - iOS Safari 17+ on iPhone is the main target. Desktop, iPad (it can't add passes) and Android get the guards.
  - WCAG 2.1 AA.
  - 44pt touch targets.
  - Dynamic Type, `prefers-reduced-motion` and dark mode.
- **Free plan:** static assets never invoke the Worker (`run_worker_first: ["/api/*"]`), and one signature uses well under 10 ms of CPU.
- **Workflow:**
  - TDD: write the failing test, run it and see it fail, implement, run it and see it pass, commit.
  - Commit messages use Conventional Commits and end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
  - Commands: `pnpm test` (all Vitest projects), `pnpm check` (svelte-check + tsc), `pnpm e2e` (Playwright).
  - Deploy: `CLOUDFLARE_ENV=<env> pnpm build && pnpm wrangler deploy`. The Vite plugin picks the environment at build time, so `wrangler deploy --env` isn't used. Secrets still go in with `wrangler secret put <NAME> --env <env>`.

## Review Focus

These are the failure modes most likely to bite real people. Each line names the task tests that pin it.
1. **An ambiguous 11-digit Pix key:** a number that is both a valid CPF and a valid mobile number, such as `11912345684`, makes the app ask "CPF or Celular" instead of guessing. Pinned by Task 6's `detectPixKey` test and Task 11's e2e "ambiguous key".
2. **Safari wiped its storage** (the 7-day rule, private browsing, cleared data): the pass's edit link restores the card with the same serial, so the re-issued pass replaces the old one. Pinned by Task 8's "round trip keeps id" and Task 11's e2e "restore after storage loss".
3. **Opened in Instagram, WhatsApp or TikTok, on a computer, on an iPad, or on Android:** a guard shows the next step, never a dead end. Pinned by Task 11's `detectEnv` matrix and its e2e guards.
4. **Signing fails** (offline in the metro, 429, 5xx): a plain error appears, nothing is lost, and retrying works. Pinned by Task 9's `SignError` kinds and Task 11's e2e "sign failure".
5. **Pasted or accented input** (`" 529.982.247-25 "`, `"José Antônio da Conceição Júnior"`, `"São Paulo"`): the card shows what was typed, while the Pix QR stays valid (ASCII only, at most 25 and 15 characters, correct CRC). Pinned by Task 5's `toPixText` tests and Task 6's payload tests.

## Tasks

### Task 0: Accounts, identifiers and a device spike (you do the account steps; the spike is throwaway)

- [ ] **You:** pick and register the domain. This plan uses `colinha.app` as a placeholder. If you choose a different one, change `SITE_ORIGIN` and `PASS_TYPE_ID` to match before anything else.
- [ ] **You:** in the Apple Developer Program, go to Identifiers and register the Pass Type ID `pass.app.colinha.card`. Create its certificate (with a CSR from Keychain Access) and export the certificate and key as `Certificates.p12`. ```

SignedData  = SEQ{ INT 1,
                   SET{ SEQ{ OID 2.16.840.1.101.3.4.2.1 } },        -- sha256, parameters absent
                   SEQ{ OID 1.2.840.113549.1.7.1 },                 -- detached: no eContent
                   [0] IMPLICIT { signer cert, then the WWDR cert },
                   SET{ SignerInfo } }
SignerInfo  = SEQ{ INT 1, SEQ{ issuer, serial }, SEQ{ OID sha256 },
                   [0] IMPLICIT signedAttrs,
                   SEQ{ OID 1.2.840.113549.1.1.1, NULL },          -- rsaEncryption
                   OCTET STRING signature }
signedAttrs = setOf(
   SEQ{ OID 1.2.840.113549.1.9.3, SET{ OID 1.2.840.113549.1.7.1 } },  -- contentType = data
   SEQ{ OID 1.2.840.113549.1.9.5, SET{ UTCTime(at) } },               -- signingTime
   SEQ{ OID 1.2.840.113549.1.9.4, SET{ OCTET STRING digest } })       -- messageDigest
signature   = crypto.subtle.sign('RSASSA-PKCS1-v1_5', key, signedAttrs encoded with tag 0x31)

**Payload:** each element is its 2-digit id, then the value's length as 2 digits, then the value. The elements go in this order:
1. `00`: `01`
2. `26`: `00` `br.gov.bcb.pix`, then `01` the key
3. `52`: `0000`
4. `53`: `986`
5. `58`: `BR`
6. `59`: `toPixText(name, 25)`
7. `60`: `toPixText(city, 15)`
8. `62`: `05` `***`
9. `6304` followed by `crc16` of everything before it, including `6304`

There is no field `01`. Banco Central's manual makes it optional, and its value `12` would mark the code single-use.
